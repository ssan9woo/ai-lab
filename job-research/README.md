# Job Research — AI-Native Engineering 실험

## 이게 뭔가

[ai-job-search](https://github.com/MadsLorentzen/ai-job-search)를 참고해서 만드는 **경량판 job research 시스템**. 목표는 실전에서 잘 동작하는 것으로 알려진 오픈소스 agent 시스템의 설계를 직접 뜯어보고, 같은 구조적 사고를 작은 스케일로 재현하면서 AI-native engineering(스킬 분해, 컨텍스트/상태 관리, evidence 기반 판단, 신뢰 경계 설계)에 익숙해지는 것.

**기능 자체(구직)가 목적이 아니라, 시스템을 그렇게 만든 이유를 이해하는 게 목적이다.** 원본 대비 기능은 얇게, 구조적 결정은 최대한 그대로 따라간다.

## 원본과의 관계

| | ai-job-search (원본) | 이 프로젝트 |
|---|---|---|
| 범위 | 탐색 → 평가 → CV/커버레터 작성 → 인터뷰 준비 → 결과 추적까지 풀 파이프라인 | 탐색 → 요구사항 구조화 → evidence matching → fit/gap → 지원 추천까지만 (문서 작성/자동 지원 제외) |
| 목적 | 실사용 구직 도구 | 그 도구의 설계를 학습하기 위한 축소 재현 |
| 진행 방식 | 이미 완성된 시스템 | 스텝별로 하나씩, 매 스텝마다 원본이 왜 그렇게 만들었는지 먼저 공부하고 우리 버전을 만듦 |

전체 요구사항 정의는 상위 문서(`personal-job-analysis-agent-skill.md`, V1 범위/Non-goals/성공 기준)를 따른다.

## 핵심 설계 결정 (원본에서 배워서 채택한 것)

### 1. 멀티 스킬 아키텍처
하나의 거대한 스킬이 아니라, 책임별로 독립된 스킬 + 이를 오케스트레이션하는 커맨드로 구성한다. 원본의 `job-scraper` / `job-application-assistant` / `upskill` 스킬 분리가 이 프로젝트의 8.1~8.6 컴포넌트 경계와 거의 대응된다.

**스킬 vs 커맨드 경계**: 자연어 트리거로 반복 매칭되어야 하는 도메인 실행 로직은 스킬로, 사용자가 명시적으로 저빈도 호출하는 온보딩/오케스트레이션 작업은 커맨드로 둔다. 원본의 `/setup`이 스킬이 아니라 커맨드인 이유가 이것이고, `candidate-profile`도 같은 이유로 스킬이 아니라 커맨드로 둔다 (`.claude/commands/candidate-profile.md`).

### 2. Fork-and-own 모델 (멀티테넌트 아님)
스킬 로직(절차)은 범용이지만, 실행되는 이 저장소 자체가 개인 인스턴스다. Candidate Profile은 런타임 인자로 매번 넘기는 게 아니라, 스킬 폴더 안 데이터 파일로 존재하며 각 스킬이 그 파일을 그냥 읽는다.

### 3. Candidate Profile 부트스트래핑
원본은 `/setup` 커맨드가 세 가지 입력 경로(문서 폴더 자동 읽기 / 단일 CV 첨부 / 대화형 인터뷰)를 모두 지원하고 하나의 구조화된 프로필로 수렴시킨다. 우리는 `/candidate-profile` 커맨드가 이 역할을 맡는다. 1단계는 단일 소스 첨부 경로만 지원 (이력서 + 있으면 면접 준비 노트 등 보강 자료).

### 4. 개인정보 경계
- 원본 이력서, 연락처, 지원 기록 등 민감 데이터는 `.gitignore`로 완전 차단
- 구조화된 프로필 md는 커밋 대상(향후 원본 프레임워크 업데이트를 merge로 받기 위함)이지만, 저장소 자체를 private으로 유지하는 것을 전제로 함 — GitHub의 "Fork" 기능은 원본이 public이면 강제로 public이 되므로 쓰지 않는다.

### 5. Evidence before conclusion
원본이 `[Inferred from ... - review before relying on this]` 같은 라벨로 추론과 원문 근거를 구분하듯, 이 프로젝트도 프로필/매칭 판단 모두 원문에 없는 내용은 추측하지 않고 `확인 불가`로 명시한다 (상위 문서 9.1, 9.3 원칙).

## 진행 방식

한 번에 전체를 만들지 않는다. 스텝마다:
1. 원본이 해당 부분을 어떻게 만들었는지, 왜 그렇게 만들었는지 먼저 확인
2. 우리 스코프에 맞게 축소/응용해서 설계
3. 실제 데이터(이력서, 공고)로 검증

### 스텝 진행 상황

- [x] **Step 1 — Candidate Profile 커맨드**: 이력서 + 면접 준비 노트를 구조화된 프로필로 변환 (`/candidate-profile`, `profile.md` 생성 완료)

- [ ] Step 3 — 공고 요구사항 구조화
- [ ] Step 4 — Evidence matching
