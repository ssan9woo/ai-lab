# Flutter 자연어 UI 검증 CLI

## 이게 뭔가요

자연어 문장 하나로 Flutter 앱의 UI 플로우를 검증하는 로컬 CLI 실험. "로그인해서 환영 메시지 확인해줘" 같은 문장을 주면, 실제 iOS 시뮬레이터에서 그 플로우를 실행하고 pass/fail을 알려준다.

로그인 화면 + 할 일 리스트로 구성된 작은 테스트용 Flutter 앱을 대상으로, 자연어 → 테스트 실행 → 결과 리포트까지 이어지는 파이프라인 전체를 손으로 만들어본 1차 실험.

## 왜 만들었나

[Kane CLI](https://www.testmuai.com/kane-cli/)(자연어로 브라우저 플로우를 검증하는 상용 도구)를 보고 든 질문 — "AI가 코드는 순식간에 짜는데, 그게 실제로 동작하는지 검증하는 건 여전히 사람이 수동으로 한다"는 문제의식을 그대로 흉내 내보고 싶었다.

목적은 제품화가 아니라, **자연어 기반 에이전틱 테스트 워크플로우가 실제로 구성 가능한지**, 어떤 구조로 동작하는지, 어디서 막히는지를 직접 만들어보며 확인하는 것. NL 파싱 기술 자체를 연구한 게 아니라, "이런 워크플로우를 실제로 조립할 수 있는가"를 실험한 것에 가깝다.

## 어떻게 동작하나

```
자연어 지시
    │
    ▼
┌─────────────────────┐
│  자연어 → 액션 플랜   │   LLM은 정해진 액션 어휘(탭/입력/검증 등)로만
│  (구조화된 출력)      │   번역 — 자유 실행이 아니라 좁은 매핑만 담당
└─────────────────────┘
    │  JSON 액션 플랜
    ▼
┌─────────────────────┐
│  액션 플랜 → 실행     │   시뮬레이터에서 실제 위젯을 조작/검증
│  (위젯 트리 조작)     │   스텝 하나 실패해도 나머지는 계속 진행
└─────────────────────┘
    │
    ▼
터미널 요약 (✓/✗, 소요시간) + 로컬 evidence 기록 (지시문 · 플랜 · 결과)
```

핵심 설계 원칙: **LLM은 "무엇을 할지"만 좁게 결정하고, "어떻게 할지"는 전부 결정론적 코드가 처리한다.** LLM이 직접 앱을 조작하지 않는다.

## 실행 방법

사전 준비:
- Flutter SDK, iOS 시뮬레이터
- 로그인된 [Claude Code CLI](https://claude.com/product/claude-code) (`claude` 명령어) — 별도 API 키 불필요, 이미 인증된 CLI를 그대로 활용

```bash
cd flutter-nl-verify
./verify "test@test.com / 1234로 로그인해서 환영 메시지 확인해줘"
```

시뮬레이터가 안 켜져 있으면 자동으로 하나를 찾아 부팅한 뒤 실행한다.

## 실행 예시

**성공 케이스**

```
$ ./verify "test@test.com / 1234로 로그인해서 환영 메시지가 보이는지 확인해줘"

NL Verify Summary
Steps: 4 | Passed: 4 | Failed: 0
Total duration: 5207ms
✓ enterText(email_field) 1946ms
✓ enterText(password_field) 1798ms
✓ tap(login_button) 1463ms
✓ expectVisible(welcome_message) 0ms
Evidence: evidence/20260821_125941
```

같은 의도를 다른 문장으로 줘도("로그인 화면에서 이메일 test@test.com 비밀번호 1234 입력하고 로그인 버튼 눌러서 환영 문구가 뜨는지 봐줘") 동일한 액션 플랜으로 수렴함을 확인했다.

**실패 케이스**

```
$ ./verify "존재하지 않는 logout_button 위젯을 눌러줘"

NL Verify Summary
Steps: 1 | Passed: 0 | Failed: 1
✗ tap(logout_button) 4ms
  Bad state: Expected exactly one widget for target(by: key, value: logout_button), found 0.
Evidence: evidence/20260821_120305
```

예외로 죽지 않고 실패 사유가 evidence에 그대로 기록된다.

## 한계와 실무 도입 가능성

**되는 것**: 미리 정의된 화면·위젯을 대상으로, "정확한 지시 → 확정적인 플로우" 검증은 안정적으로 동작한다. 반복적인 스모크 테스트 용도로는 실용적 가치가 있어 보인다.

**막히는 지점**

- **결정론적 플로우까지만 가능**: "가장 싼 상품 결제까지" 같이 실행 중 실제 데이터(가격 비교 등)를 봐야 다음 행동이 정해지는 플로우는, "자연어를 실행 전에 한 번에 통째로 액션 플랜으로 번역"하는 구조로는 원천적으로 처리할 수 없다. 이런 플로우는 매 스텝마다 화면을 다시 관찰하고 판단하는 반복 루프 구조가 필요하다 — Kane 같은 도구가 스크린샷 기반 인식을 함께 쓰는 이유이기도 하다.
- **재료(vocabulary)는 결국 사람이 준비**: LLM은 자유 형식 문장을 이해하는 것처럼 보이지만, 실제로는 미리 등록된 위젯 이름·변수 집합 안에서만 매핑한다. 이 프로젝트는 그 목록을 코드에 직접 박아뒀는데, Kane은 `{{username}}` 같은 변수 플레이스홀더 + 별도 secret 저장소로 이를 분리한다. 다만 그 변수 자체도 Kane에서 자동으로 채워지는 게 아니라 사람이 JSON으로 직접 등록해야 한다 — **"자연어 이해"보다 "재료 관리"가 이 종류 도구의 실제 병목**이라는 게 이번 실험의 결론.
- **자격증명을 코드에 하드코딩**: 이 실험은 테스트 계정을 그대로 프롬프트에 노출시켰다. 실무에 쓰려면 Kane처럼 지시문과 민감정보를 분리하는 계층이 최소 요건이다.

**결론**: Kane 같은 상용 SaaS가 파는 것은 "자연어 이해 능력"이라기보다, 그 위에 얹힌 인프라(실기기 클라우드, 병렬 실행 그리드, 팀 대시보드)에 가까워 보인다. NL 파싱 레이어 자체는 이번 실험처럼 기존 CLI 도구 조합만으로도 개인 수준에서 며칠 안에 재현 가능했다.
